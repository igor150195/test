# Дорожная карта улучшений генератора

Дата: 2026-10-16. Целевое место: `docs/generator/improvement-roadmap.md`.
Опирается на `generator-audit.md` (проблемы G-xx, риски R-xx), `skills-audit.md` (S-x) и `learning-architecture.md`.

**По условию аудита ничего из перечисленного не реализовано.** Реализацию нужно начинать отдельным заданием.

Размеры: **S** — часть дня; **M** — 1–3 дня; **L** — больше. Это относительные оценки, не обещания по срокам.

## 1. Приоритетные изменения

Для каждой рекомендации даны все восемь пунктов из задания: проблема, подтверждение, решение, затрагиваемое, зависимости, проверка, риски, цена отсрочки.

### P0 — критично

#### P0-1. Защитить сгенерированный CSS от перезаписи (G-01) — размер S

- **Проблема:** `project-styles build` на старом проекте стирает сгенерированный CSS; имя `css/custom.css` имеет два смысла.
- **Подтверждение:** прогон: `fashion-store/css/custom.css` 9 421 → 395 байт.
- **Решение:** (а) `build` отказывается писать в существующий файл, не помеченный как собственный вывод (заголовок `/* generated by project-styles */`), и требует `--force`; (б) для проектов без `styles/custom.scss` команда `build` не создаёт его молча; (в) закрепить правило имён: `css/project.css` — генерируется, `css/custom.css` — вывод `custom.scss`; для трёх существующих проектов — манифест «legacy: css/custom.css сгенерирован».
- **Затронутое:** `scripts/project-styles.mjs`, `scripts/tests/project-styles.test.mjs`, `site-from-reference/SKILL.md` (шаг инициализации), `design-system/templates/project/README.md`.
- **Зависимости:** нет.
- **Проверка:** добавить тест «`build` не затирает существующий файл без заголовка»; повторить прогон на копии `fashion-store`.
- **Риски:** небольшие; изменение поведения команды — отразить в `changelog.md`.
- **Если отложить:** любая ошибочная команда уничтожает работу проекта (в рабочей копии без истории — безвозвратно).

#### P0-2. Контракт проекта и самодостаточная сборка (G-02, R-01) — размер L

- **Проблема:** сайт не переносится из репозитория; версия DS не закреплена.
- **Подтверждение:** `../../dist/css/*.css` во всех проектах; 138 абсолютных `url("/design-system/sets/…")` в `icons.css`; `/dist/` в `.gitignore`.
- **Решение:**
    1. `projects/<slug>/project.json` — слаг, тип, платформа, версия генератора и DS, список страниц, внешние зависимости, режим (`reference|brief`), владельцы файлов (`generated|owner`).
    2. Параметр Sass `$icon-base` для пути к спрайту вместо захардкоженного `/design-system/sets/`.
    3. Команда `npm run site:build -- <slug>` → `projects/<slug>/dist/` с объединёнными и версионированными CSS, нужным спрайтом и ресурсами; относительные пути.
    4. В `project.json` закреплять `ds_version`; обновление DS на живом сайте — осознанное действие.
- **Затронутое:** `design-system/tokens/icons.css` (общий ресурс — **требует согласования** по `AGENTS.md`, раздел 8), `design-system/scss/tokens.scss`, новый скрипт в `scripts/`, шаблон проекта, `generator-guide.md`.
- **Зависимости:** P0-1 (имена файлов).
- **Проверка:** собрать `dist` проекта, раздать из произвольного подкаталога (`/some/path/`), прогнать раннер: 0 запросов ≥400, 0 сломанных иконок и стилей.
- **Риски:** затрагивается общий `icons.css`; для обратной совместимости значение `$icon-base` по умолчанию оставить прежним.
- **Если отложить:** ни один сайт нельзя безопасно опубликовать; каждое обновление DS рискует изменить живые проекты.

#### P0-3. Внешние ресурсы и права на них (G-03) — размер M

- **Проблема:** 34 изображения из двух проектов грузятся с чужих доменов; учёта прав нет.
- **Подтверждение:** `fashion-store` → `clothing-shop.oml.ru` (10 `<img>`), `test-site` → `hr.tutu.ru` (24 `<img>`); 0 документов с упоминанием лицензии.
- **Решение:** манифест `projects/<slug>/assets.json` (источник, права `own|licensed|placeholder|unknown`, локальный путь, ratio, фокус, роль); проверка `check:assets`, которая в продакшен-сборке отклоняет `http(s)` в `src`/`url()` и ресурсы со статусом `unknown`; шаг «локализовать ресурс» с пометкой `placeholder` при отсутствии прав. Стороннее оформление бренда (как в `test-site`) помечается как учебная копия и не публикуется.
- **Затронутое:** новый скрипт, `site-from-reference/SKILL.md` (пункт про изображения), `reference-analysis-template.md` (манифест ресурсов), `AGENTS.md` (короткое правило).
- **Зависимости:** P0-2 (`project.json`).
- **Проверка:** `check:assets` проваливается на текущих `fashion-store` и `test-site` (это ожидаемо, фиксирует долг) и проходит на `house-store`.
- **Риски:** юридическое решение по сторонним брендам принимает человек.
- **Если отложить:** недоступность картинок на публикации и правовая уязвимость; baseline-скриншоты нестабильны.

#### P0-4. Тематизация (G-04) — размер M

- **Проблема:** производные токены вычисляются на `:root`; тема на классе проекта не доходит до `--flags_spec_bg`, `--primary_N`; фиолетовые элементы в двух проектах.
- **Подтверждение:** `new_sizes.css:1741` `--flags_spec_bg: var(--primary)`; 19 использований `primary_N` в components/blocks/core; рендеры `fashion-store` и `house-store`.
- **Решение:** официальный контракт `theme`: файл `styles/theme.scss`, который **компилируется в `:root`** и выводит всю цепочку (`primary_1…9`, `on_primary_*`, `flags_*`, фокус-кольцо) из нескольких исходных цветов (Sass-карта или `color-mix`). Для DS: сделать `--primary_N` производными (изменение общего токена — **с согласования**). Проверка «протечки» — рендер набора компонентов с темой и поиск вычисленных цветов, равных дефолтной палитре.
- **Затронутое:** `design-system/tokens/new_colors.css`, `new_sizes.css` (флаги), `scss/tokens.scss`, шаблон проекта, `tokens.md`, оба проекта с темой.
- **Зависимости:** P0-2 (сборка проекта), согласование изменения общих токенов.
- **Проверка:** `check:theme` — на странице с каждым `.ds-*` ни один вычисленный `color/background/border-color` не равен `rgb(112, 66, 244)` (дефолтный primary), кроме явно разрешённых.
- **Риски:** изменение значений общих токенов влияет на все проекты — выполнить на ветке со сравнением снимков.
- **Если отложить:** каждый проект вручную заплатывает те же протечки (как `fashion-store`: переопределены только `primary_1…4`); декларация «одна система — много сайтов» остаётся недостоверной.

#### P0-5. Шлюз соответствия и универсальный QA-раннер (G-05, G-06, G-15) — размер L

- **Проблема:** Design System First не проверяется; QA привязан к `fashion-store`; матрица скилла не реализована; приёмка самооценкой.
- **Подтверждение:** 0 из 3 `token-map.md` со статусами; `playwright.visual-qa.config.mjs` — `testMatch: 'fashion-store.spec.mjs'`; в spec 3 кадра вместо матрицы.
- **Решение:**
    1. `npm run qa -- <slug>`: читает `project.json`, снимает 4 viewport × (первый экран, полная страница, сегменты), собирает программные проверки (консоль, запросы, битые изображения, overflow, внешние хосты, неопределённые токены, неопределённые иконки, класс из HTML ↔ правило в CSS, axe-core, вес ресурсов, `width/height`/`lazy`) в `results.json` по схеме.
    2. `npm run check:project -- <slug>`: наличие и формат документов, статусы в `token-map.md`, обязательный `design-system-gap-report.md` при `EXTEND/BLOCKED`, отсутствие локального CSS для секции со статусом `EXTEND`.
    3. Оценка делится на программную и экспертную; агент заполняет только экспертную часть после программного отчёта.
    4. Привести `house-store` и `test-site` к формату (ретроспективные `token-map`, `qa-report`).
- **Затронутое:** `scripts/visual-qa/*` (обобщить), `playwright.visual-qa.config.mjs`, `visual-qa/SKILL.md`, `visual-qa-checklist.md`, `evaluation-suite.md`, новый `check:project`.
- **Зависимости:** P0-2 (`project.json`); axe-core — **новая dev-зависимость**, требует отдельного обоснования по `AGENTS.md` (раздел 8): без него доступность остаётся непроверяемой.
- **Проверка:** раннер на трёх проектах даёт `results.json` с одинаковой схемой; `check:project` ожидаемо находит текущие нарушения (`test-site` EXTEND, `house-store` без docs).
- **Риски:** нестабильность на другой ОС и версии браузера — зафиксировать версию Chromium в документации и использовать суффикс платформы у baseline.
- **Если отложить:** главная политика остаётся честным словом агента; регрессии не ловятся.

#### P0-6. Единый источник истины для инструкций (G-07, S-1, S-2) — размер S

- **Проблема:** контрадикторные копии; устаревший `overview.md`; сломанная нумерация; пустой каталог.
- **Подтверждение:** 7 из 7 файлов kit отличаются; `overview.md` утверждает, что компонентов и проектов нет; шаги 6 и 7 повторяются.
- **Решение:** удалить `codex-site-generation-kit/` (или заменить скриптом экспорта из рабочих файлов); обновить `overview.md` по факту (с датой и ссылкой на исходники); исправить нумерацию; удалить пустой `design-system/knowledge-base/`; оставить правило Design System First только в `design-system-first.md`, остальное — ссылки.
- **Затронутое:** перечисленные файлы, `AGENTS.md` (ссылка).
- **Зависимости:** нет.
- **Проверка:** скрипт `check:docs` — нет двух файлов с одинаковым именем и разным содержимым; все относительные ссылки ведут к существующим файлам.
- **Риски:** минимальные; перед удалением kit убедиться, что он не используется как пакет передачи в другое окружение (вопрос к владельцу).
- **Если отложить:** агент, открывший не тот файл, получит более слабые правила.

## 3. Этапы внедрения

| Этап | Содержание | Критерий готовности |
|---|---|---|
| **1. Стабилизация** | P0-1, P0-6, P2-7, P1-1 (`check:tokens`, `check:docs`) | `build` не стирает файл (тест); kit удалён; `overview.md` соответствует факту; проверки токенов и ссылок проходят |
| **2. Контракт проекта и перенос** | P0-2, P0-3 | `site:build` создаёт `dist` проекта; проект работает из подкаталога без запросов ≥400; `check:assets` проходит у `house-store` |
| **3. Единая проверка** | P0-5, P1-5, P1-6 | `qa` работает на трёх проектах; `check:project` фиксирует исходный долг; `results.json` по схеме |
| **4. Тематизация** | P0-4 | `check:theme` проходит; оба темизированных проекта без фиолетовых протечек |
| **5. Знания и каталог** | P1-2, P1-3, P1-4, P1-7 | Валидатор проходит; `catalog.json` покрывает все `.ds-*`; оценочный набор C1–C3 имеет базовый разброс |
| **6. Масштабирование** | P2-1…P2-6 по условиям запуска | По каждому пункту — своё условие |

Этап 4 можно поставить сразу после этапа 2 (он не зависит от 3), если приоритет — визуальное качество, а не проверки.

## 4. Ожидаемая польза

| Этап | Польза |
|---|---|
| 1 | Исчезает риск потери работы и ложных инструкций; цена минимальна |
| 2 | Сайты можно публиковать; обновления DS перестают быть угрозой |
| 3 | Политика становится проверяемой; приёмка объективна |
| 4 | Один дизайн-код — разные бренды без заплаток |
| 5 | Накопление знаний начинает давать измеримый эффект |

## 5. Риски плана

| Риск | Смягчение |
|---|---|
| Рост инфраструктуры раньше, чем число проектов | Делать минимум по этапу, не расширять базу до измеренной пользы (принцип из `learning-architecture.md`) |
| Изменения общих файлов ломают существующие проекты | Ветка + сравнение снимков + согласование (правило `AGENTS.md`) |
| Новая зависимость (axe-core, оптимизатор изображений) | Обоснование и запись в `changelog.md`; без axe доступность остаётся непроверяемой |
| Перегрузка агента длинными инструкциями | Индекс чтения; вынос проверяемого в команды |

## 6. Ответы на итоговые вопросы

1. **Состояние генератора.** Хороший процессный каркас и визуально сильные результаты при слабой технической проверяемости: правила в основном словесные, ресурсы не переносимы, тематизация протекает.
2. **Готовность к реальным проектам.** Для статических одностраничных сайтов — под присмотром человека. Для публикации «как есть», многостраничности и живой интерактивности — не готов.
3. **Сохранить.** Design System First и четыре статуса; культуру честной отчётности; нейтральный API против платформенных адаптеров; `custom.scss` и тест его сохранности; жизненный цикл знаний; статический сервер; нативные решения без JS.
4. **Что сильнее всего ограничивает качество.** Протекающая тематизация (G-04); мало секций (R-05); отсутствие автоматического шлюза соответствия и общего QA (G-05, G-06); потеря контроля над ресурсами (G-02, G-03).
5. **Какие скиллы улучшить.** `site-from-reference` (нумерация, входы/выходы/состояние, индекс чтения, режим без диалога) и `visual-qa` (раннер, разделение программной и экспертной оценки).
6. **Какие скиллы нужны.** `site-from-brief` и `knowledge-capture`. Остальные компетенции — инструменты и проверки.
7. **Библиотека блоков.** Метаданные в `index.md` → `catalog.json` → поиск; новые секции только по правилу двух проектов, начиная с уже реализованных локально.
8. **База знаний.** Markdown + YAML в git, схема, генерируемый реестр, `kb:search`; без БД и векторов до выполнения условий пересмотра.
9. **Контролируемое самообучение.** Автоматика пишет только в `knowledge/inbox/` и `reports/`; изменения DS и скиллов — через шлюз с оценочным набором и утверждением человека; откат через `git revert` и версии генератора.
10. **Ручные правки и продакшен.** `styles/custom.scss` — собственность владельца, подключается последним, защищён тестом и правилом; генерируемое и ручное разделены именами и манифестом; DS закрепляется версией; сайт собирается в `dist` проекта без зависимости от путей репозитория (P0-1, P0-2).
11. **Проверки в первую очередь.** Защита от перезаписи; сборка проекта из подкаталога без запросов ≥400; проверка внешних ресурсов; `check:project` (документы и статусы); `check:tokens`; тема без фиолетовых протечек.
12. **Три–пять изменений с наибольшим эффектом.** (1) P0-2 контракт проекта и перенос; (2) P0-5 шлюз соответствия и общий QA; (3) P0-4 тематизация; (4) P0-3 управление ресурсами; (5) P1-2/P1-3 схема знаний и каталог.
13. **Как измерить улучшение.** Оценочный набор C1–C3, три прогона на версию, сравнение парами, 60 % объективных показателей (раздел 9 `learning-architecture.md`); допуск регрессии −3 пункта; жёсткие отказы.
