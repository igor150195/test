## 1. Контраст текста скидки

### Подтверждённые факты

Цепочка нейтрального компонента ровно такая:

```
.ds-price__discount
  -> color: var(--price_sale_color)
  -> --price_sale_color: var(--sale)
  -> --sale: #FF6231
```

Её задают соответственно `design-system/components/price/_price.scss:33`,
`design-system/tokens/new_sizes.css:1357` и
`design-system/tokens/new_colors.css:148`. На светлой поверхности
`#F2F0E9` фактическая пара `#FF6231` / `#F2F0E9` имеет контраст **2.61:1**;
она не проходит AA для обычного текста.

`--sale` также является не только текстовым цветом:

| Потребитель | Цепочка | Роль | Последствие замены `--sale` |
|---|---|---|---|
| `.ds-flag--sale` | `--flags_action_bg` → `--sale` | заливка флага | изменится цвет всех нейтральных sale-флагов |
| `.ds-badge--sale` | `background-color: var(--sale)` | заливка бейджа | изменится цвет всех нейтральных sale-бейджей |
| `.ds-price__discount` | `--price_sale_color` → `--sale` | текст цены | изменится цвет текста скидки |
| legacy token `--gr_card_type_2_shadow_h` | `inset … var(--sale)` | hover-граница карточки | текущего прямого потребителя в исходниках не найдено; при появлении изменится её цвет |
| legacy token `--gifts_item_bg` | `var(--sale)` | фон подарочного элемента | текущего прямого потребителя в исходниках не найдено; при появлении изменится его фон |

`--flags_action_bg` и `--flags_action_color` определены в
`new_sizes.css:1738-1739`; на `.ds-flag--sale` они применяются в
`components/badge/_badge.scss:44-46`. `--on_sale` сейчас равен `#000000`.
Это даёт для текста на sale-заливке **7.04:1** и проходит AA.

Проверенные пары текущей палитры:

| Передний цвет | Поверхность | Контраст | Назначение/вывод |
|---|---:|---:|---|
| `#FF6231` | `#F2F0E9` | 2.61:1 | наблюдаемая ошибка текста скидки |
| `#FF6231` | `#FFFFFF` (`--bg_main`) | 2.98:1 | также не подходит для обычного текста |
| `#FF6231` | `#F7F7F7` (`--bg_main_surface`) | 2.78:1 | также не подходит для обычного текста |
| `#FF6231` | `#151037` (`--on_bg_main_accent`) | 6.07:1 | проходит на дефолтном тёмном Footer |
| `#000000` (`--on_sale`) | `#FF6231` (`--sale`) | 7.04:1 | sale-заливка с её штатным текстом проходит |

### Варианты

| Вариант | Суть | Влияние на проекты | Проверка | Откат |
|---|---|---|---|---|
| **A. Разделить текст и заливку** | Добавить новый публичный токен, например `--price_sale_text_color`, и направить в него `--price_sale_color`; оставить `--sale` цветом заливок | Меняется только Price там, где нет локального переопределения. Flag, Badge и legacy-поверхности сохраняют текущий цвет | Проверить `#B64D31` на `#F2F0E9` (4.50:1), на белом (5.13:1); собрать; сравнить вычисленный `color` Price и фоны Flag/Badge; QA house-store и visual QA fashion-store | Удалить новый alias и вернуть `--price_sale_color: var(--sale)`; обратимый одной правкой токена/Price |
| **B. Локальное правило темы** | Каждый проект сам задаёт `--price_sale_color` после общих токенов | Исправляет только согласованные проекты; новые и старые сайты остаются разными, а дефолтный DS-дефект сохраняется | `check:theme` и QA каждого проекта; вручную проверять все светлые поверхности | Удалить локальное переопределение. Не устраняет дефект в общей библиотеке |
| **C. Изменить `--sale`** | Заменить базовый `--sale`, например на более тёмный `#B64D31` | Изменяет одновременно Price, Badge, Flag и потенциальные legacy-поверхности во всех проектах; меняет брендовый визуальный акцент | Полный набор QA трёх проектов, а также сравнение вычисленных `--sale*`, Flag/Badge/Price и legacy fixtures | Вернуть одно значение `--sale`, но внешние скриншоты и проекты уже увидят изменение |

`#B64D31` — ближайший по поканальному расстоянию к текущему `#FF6231`
пример, найденный при переборе RGB, который достигает 4.50:1 на `#F2F0E9`.
Это **кандидат для проверки**, а не утверждённый брендовый цвет.

### Рекомендация

Выбрать **A**: это единственный вариант, который отделяет семантику текста
от семантики заливки и не меняет флаги/бейджи у всех сайтов. Вариант B годится
лишь как временное исключение в конкретном проекте. Вариант C не рекомендован
без отдельного визуального согласования всех потребителей.

## 2. Конфликт `--toggle_title_icon_h`

### Подтверждённые факты

В `design-system/tokens/new_sizes.css` переменная объявляется дважды:

```css
/* строки 329–335 */
--toggle_title_icon_h: 32px;
--toggle_title_icon_w: 32px;
--toggle_title_icon: var(--icon_arrow_bot_md);

/* строки 341–343 */
--toggle_title_icon_h: var(--icon_arrow_bot_md);
--toggle_title_icon_color_h: var(--icon_bg_main_6);
```

В CSS второе объявление побеждает: вычисленным значением
`--toggle_title_icon_h` становится URL-маска, а не длина. При этом базовый
`--toggle_title_icon` **уже существует** на строке 335. Суффиксы `_h` и `_a`
в соседних свойствах используются как hover/active-состояния; это конфликтует
с более ранним `_h` как height.

Поиск вне `new_sizes.css` не нашёл ни одного фактического потребителя
`--toggle_title_icon_h`, `--toggle_title_icon` или `--toggle_title_icon_a` в
SCSS, CSS либо HTML. Следовательно, нельзя доказать, какой из двух публичных
смыслов ожидался существующей разметкой: ошибка реальна, но авторское
намерение второго свойства не подтверждено.

### Варианты

| Вариант | Точная правка | Влияние | Проверка | Откат |
|---|---|---|---|---|
| **A. Сохранить `_h` как высоту** | Оставить `--toggle_title_icon_h: 32px`; переименовать вторую строку в новый недвусмысленный hover-токен, например `--toggle_title_icon_hover: var(--icon_arrow_bot_md)` | Восстанавливает значение height. Новый hover-token пока никто не использует. Это меняет вычисленное `--toggle_title_icon_h` с URL на `32px` | Сравнить computed token до/после; добавить fixture будущего Toggle, где высота 32px и hover-mask берётся отдельно; `check:tokens`, build | Вернуть вторую строку с прежним именем и удалить новый token |
| **B. Сохранить `_h` как hover-иконку** | Переименовать первый токен в `--toggle_title_icon_height: 32px` | Изменяет публичное значение существующего `--toggle_title_icon_h` не меньше, чем A, и ломает потенциальных потребителей высоты | Требует поиска внешних потребителей за пределами репозитория; без него безопасно проверить нельзя | Вернуть прежнее имя высоты |
| **C. Удалить вторую строку без hover API** | Удалить второй конфликтующий declaration | Возвращает высоту 32px, но не предоставляет вариант иконки на hover | Проверить, что никакая существующая сборка не ссылалась на hover-token; `check:tokens`, build | Вернуть строку (но дефект вернётся) |

### Рекомендация

Выбрать **A**, но только после внешнего поиска потребителей публичного token API:
`_h` уже широко используется в файле как сокращение hover, однако именно
`--toggle_title_icon_h` в первой группе явно описывает размер рядом с `_w`.
Новый ясный hover-token следует подключать к будущему/подтверждённому Toggle
миксину отдельно; этот репозиторий сейчас не имеет такого потребителя.

**Изменение вычисленного CSS:** неизбежно — текущая победившая URL-строка не
является значением длины. Поэтому нельзя заявлять о визуальной эквивалентности;
нужна проверка legacy Toggle fixture до выпуска.

## 3. Три отсутствующих token URL иконок

### Подтверждённые факты

`tokens/icons.css` содержит 138 URL-переменных для существующих ID спрайта,
но не объявляет эти три:

| Отсутствующий token | Потребитель | Фактическая цепочка | Что есть в спрайте |
|---|---|---|---|
| `--icon_rating_star_lg` | legacy Rating `lg` | `--lg_rating_icon` (`new_sizes.css:1478`) → mask-image в `mixins/_rating.scss` | `icon_rating_star_sm`, `icon_rating_star_md`; ID `icon_rating_star_lg` отсутствует |
| `--icon_site_checkbox_small` | legacy Checkbox `sm` и `md` | `--sm_checkbox_icon`/`--md_checkbox_icon` (`new_sizes.css:648,665`) → mask-image в `mixins/_form_elements.scss` | `icon_check_sm`, `icon_check_md`; ID с именем `icon_site_checkbox_small` отсутствует |
| `--icon_site_checkbox` | legacy Checkbox `lg` | `--lg_checkbox_icon` (`new_sizes.css:680`) → mask-image в `mixins/_form_elements.scss` | `icon_check_sm`, `icon_check_md`; ID с именем `icon_site_checkbox` отсутствует |

Во всех трёх случаях `mask-image: var(--неопределённый-token)` становится
недействительным значением декларации. Маска не рисуется: у Rating пропадает
звёздная графика, у legacy Checkbox — графика псевдоэлемента отметки. Остальная
геометрия/фон, заданные соседними правилами, сами по себе не обязаны исчезнуть.

Подходящих **одноимённых** ID в `new.sprite.view.svg` нет. Имеются
`icon_rating_star_sm` и `icon_rating_star_md`, а также `icon_check_sm` и
`icon_check_md`; их семантическая и геометрическая пригодность для замены ещё
не подтверждена. В частности, существующий `icon_rating_star_md` имеет
нестандартную область SVG, а размер mask уже задаётся отдельными токенами.

### Варианты

| Вариант | Суть | Влияние | Проверка | Откат |
|---|---|---|---|---|
| **A. Добавить согласованные URL aliases на существующие ID** | После визуального сравнения направить `lg` Rating на `icon_rating_star_md`, Checkbox на `icon_check_sm`/`icon_check_md` в зависимости от утверждённой геометрии | Меняет только legacy `lg` Rating и Checkbox; не требует изменения спрайта | Снять legacy fixtures во всех размерах, проверить mask-size, keyboard/focus state и `check:tokens`; сравнить спрайт ID | Удалить aliases и вернуть issue; риск — снова пустые маски |
| **B. Добавить новые SVG в спрайт** | Попросить источник иконок добавить именно `icon_rating_star_lg`, `icon_site_checkbox`, `icon_site_checkbox_small`; затем добавить URL tokens | Даёт семантически точный API, но меняет общий SVG asset и требует права/визуального согласования | Проверить ID registry, сборку, URL count, visual QA legacy fixture | Удалить новые symbols и tokens в отдельном обратном изменении |
| **C. Убрать неподтверждённые legacy-варианты** | Не экспортировать `lg` Rating/legacy Checkbox с отсутствующими assets, пока не выбран A или B | Меняет/ограничивает legacy API и может сломать внешние сайты | Поиск внешних потребителей обязателен | Вернуть поддержку после A/B |

### Рекомендация

Сначала провести небольшой визуальный эксперимент для **A**: существующие
`check` и `rating_star_md` могут оказаться подходящими, но один только suffix
не доказывает эквивалентность. Если форма отметки или пропорции не совпадают,
выбрать B и запросить исходные SVG. Не следует придумывать ID или молча
подставлять несемантическую иконку.

## 4. `ds-footer__column`: класс без собственного селектора

### Подтверждённые факты

Класс является частью документированного HTML-контракта Footer:
`design-system/blocks/footer/index.md:14-24` использует
`<section class="ds-footer__column">`. Тот же класс применяется в:

- `design-system/templates/home.html` (две колонки);
- `design-system/templates/shop.html` (две колонки);
- `projects/fashion-store/index.html` (три колонки);
- `projects/house-store/index.html` (две колонки);
- `projects/test-site/index.html` (три колонки).

`design-system/blocks/footer/_footer.scss` не содержит отдельного селектора
`.ds-footer__column`. Текущая раскладка работает через родителя:

```scss
.ds-footer__columns {
    display: grid;
    grid-template-columns: repeat(auto-fit, minmax(min(100%, 180px), 1fr));
    gap: var(--section_pd_mobile);
}
```

Поэтому дочерние `section` уже становятся grid items без собственного класса.
Это объясняет корректную раскладку, но не удовлетворяет текущему эвристическому
`check:tokens`, который ищет класс в CSS буквально. `test-site` локально
переопределяет только `.tutu-footer .ds-footer__columns`, не сам column.

### Варианты

| Вариант | Суть | Влияние | Проверка | Откат |
|---|---|---|---|---|
| **A. Документировать структурный элемент и научить checker этому контракту** | Оставить CSS как есть; в Footer-doc явно зафиксировать, что `__column` — дочерний grid item без собственных declarations; добавить машиночитаемое исключение/контракт в проверку | Не меняет вычисленные стили и все проекты сохраняют вид; улучшает точность проверки | `check:tokens` должен признать только документированную пару parent/child; home/shop и три проекта; QA house-store | Откатить checker/doc, CSS не затронут |
| **B. Добавить нейтральное собственное правило** | Например, `.ds-footer__column { min-width: 0; }` с явной причиной переполнения | Может изменять min-content sizing колонок на всех сайтах; сейчас дефект переполнения не подтверждён | До/после computed styles, QA house-store, visual QA fashion-store; добавить regression fixture длинного слова | Удалить одно правило, если оно не нужно |
| **C. Убрать класс из шаблонов** | Полагаться на `section` как grid item | Ломает документированный BEM-контракт и ухудшает возможность проектных расширений | Поиск внешних потребителей и обновление HTML/docs | Вернуть class в шаблоны |

### Рекомендация

Выбрать **A**. Отдельное CSS-правило не требуется для текущей сетки и не
доказывается ни дефектом рендера, ни требованиями layout. Документации одной
недостаточно, пока checker требует буквального селектора: нужно одновременно
изменить проверку, чтобы она понимала подтверждённый структурный BEM-элемент.

## Рекомендуемый порядок последующих небольших правок

| Шаг | Изменение | Меняет вычисленные стили? | До/после проверки |
|---|---|---:|---|
| 1 | Зафиксировать legacy fixtures для Toggle, Rating `lg` и Checkbox во всех трёх размерах | нет | `npm run check:tokens`, `npm run build`, hash `dist/css/*`, computed styles fixtures |
| 2 | Принять вариант Toggle и внести только его; отдельно проверить публичное имя | да, только legacy Toggle при реальном потреблении | `check:tokens`, build, hash diff, computed token and fixture render |
| 3 | Принять Icon A или B после визуальной сверки существующих SVG | да, только затронутые legacy Rating/Checkbox | `check:tokens`, build, SVG ID registry/URL registry, fixtures |
| 4 | Внести Price вариант A либо явно отложить | да, Price discount text | `check:tokens`, build, computed colours/contrast, QA house-store, `check:theme`, `npm run visual:qa -- fashion-store` без обновления baseline |
| 5 | Исправить Footer как структурный контракт (вариант A) | нет | `check:tokens`, home/shop + три проекта, QA house-store |
| 6 | Общий регрессионный прогон и ревизия known issues | зависит от выбранных шагов | сравнение hash `dist/css`, computed styles, QA house-store, `check:theme`, visual QA fashion-store |

Перед каждым шагом, меняющим общий `design-system`, нужно получить отдельное
подтверждение. Hash `dist/css` ожидаемо изменится при любой токенной правке;
его назначение — зафиксировать точную область изменений, а не требовать
неизменности.
