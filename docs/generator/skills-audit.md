# Аудит скиллов генератора

Дата: 2026-10-16. Целевое место: `docs/generator/skills-audit.md`.
Метки достоверности те же, что в `generator-audit.md`: **[Подтверждено]**, **[Риск]**, **[Гипотеза]**.

## 0. Краткий вывод

В репозитории два действующих скилла и два их устаревших дубля. Скиллы содержательные и дисциплинированные, но:

1. Они **оркестрируют ручной процесс**, а не вызывают инструменты: из 11+ шагов `site-from-reference` автоматизирован один (`project-styles init`).
2. Скилл `visual-qa` требует матрицу снимков, которой нет в коде (G-06).
3. Один из скиллов тянет за собой **≈132 КБ** обязательного чтения.
4. Нет скилла для сценария «сайт по брифу без референса» — а именно так создан `house-store`.
5. Нет скилла для сохранения знаний, хотя это главная цель проекта.

Рекомендация: **улучшить два существующих, добавить два новых, остальное решать инструментами и проверками.** Создавать скиллы «ради покрытия» перечня из задания не нужно.

## 2. Скилл `site-from-reference` (8 437 байт)

| Параметр | Оценка |
|---|---|
| Назначение | Создать новый сайт по URL или скриншоту, используя существующую дизайн-систему. Описание в frontmatter короткое и точное |
| Активация | «Использовать при новом сайте по референсу»; исключения (мелкие правки, рефакторинг DS) указаны. Условие для сайта **без** референса отсутствует |
| Содержание | 13 пунктов (нумерация сломана: 6 и 7 повторяются), раздел «Границы» и критерии завершения |
| Инструменты | Один скрипт: `project-styles.mjs init`. Всё остальное — чтение документов и ручные действия |
| Ресурсы | `design-system-first.md`, `reference-analysis-template.md`, база знаний, `home.html`/`shop.html` |
| Соответствие архитектуре | Высокое: опирается на реальные файлы DS и политику Design System First |
| Реальное использование | Косвенно: следы есть у `fashion-store` (`generator-review.md`, `page-blueprint.md`) и `test-site` (ретроспективно). У `house-store` следов нет |
| Дублирование | Политика Design System First пересказана здесь же, хотя `AGENTS.md` запрещает дублировать |
| Зависимости | ≈132 КБ обязательного чтения: `AGENTS.md` 14,8 + `generator-guide` 8,3 + `design-system-first` 4,9 + README базы знаний 4,0 + контракты компонентов и блоков 29,2 + `tokens.md` 10,4 + `icons.md` 10,2 + `mixins.md` 18,5 + шаблон анализа 8,0 + чек-лист 8,7 + `visual-qa` 6,7 + сам скилл 8,4 (**оценка по размеру файлов**) |
| Польза для качества | Высокая в части предотвращения «самодельной дизайн-системы»; средняя в части скорости |

### Недостатки

1. **Нет проверяемого результата.** Критерий завершения («проект завершён, когда документы согласованы с DOM») невозможно проверить без человека. Формат `token-map.md` не определён схемой: у существующих проектов статусов 0 из 3 (G-05).
2. **Состояние не сохраняется между шагами.** Нет файла, фиксирующего, на каком шаге находится генерация, какие версии скилла и DS использованы, какие записи базы знаний применены.
3. **Нет режима «без подтверждения».** Стоп-условие требует явного ответа пользователя; если агент работает без диалога, поведение не определено.
4. **Шаг 6 (инициализация стилей) опасен для старых проектов:** защита от стирания `css/custom.css` только словами (G-01).
5. **Размер и смешение ролей:** одновременно оркестрация, политика, правила стилей и критерии приёмки.

### Что исправить

- Починить нумерацию.
- Вынести проверяемые части в команду `npm run check:project -- <slug>` (структура документов, наличие статусов, согласованность классов и иконок).
- Заменить фразу «прочитай всё» на **индекс чтения** по фазам: для старта — `AGENTS.md` + один файл «сводка контрактов», остальное подключается по необходимости.
- Добавить блок «Входы / Выходы / Состояние» (машинно-читаемый файл `projects/<slug>/project.json`).

## 3. Скилл `visual-qa` (6 676 байт)

| Параметр | Оценка |
|---|---|
| Назначение | Отрендерить сайт, проверить адаптивность и расхождения, исправить топ-проблемы |
| Активация | «После реализации или заметного изменения вёрстки» — корректно |
| Содержание | 12 шагов + «обязательная матрица»: 4 viewport × (первый экран, полная страница, сегменты с перекрытием 20–25 %) на **каждый** маршрут |
| Инструменты | Ссылка на `npm run visual:qa` — работает **только** для `fashion-store` (G-06) |
| Реальное использование | `test-site`: сохранена полная матрица (в т. ч. `results.json`, сегменты `segment-000-y0.png…`). У `house-store` отчётов нет |
| Дублирование | Часть требований повторяет `visual-qa-checklist.md` (8,7 КБ) и `visual-qa-pipeline.md` |
| Критерий приёмки | «Не менее 85/100», оценивает сам агент-автор (G-15) |

### Недостатки

1. **Стандарт без кода.** Матрицу производил вручную агент; скрипта нет (в репозитории не найден). Следующий агент получит команду, которая работает на другом проекте.
2. **Приёмка самооценкой.** Для `fashion-store` самооценка 87,5, независимая 70.
3. **Не измеряет доступность и производительность** (нет axe, нет метрик веса и CLS), хотя перечисляет «доступность» словами.
4. **Нет перехода от визуальных находок к знаниям:** результаты матрицы не превращаются в структурированные данные для базы знаний.
5. **Смешивает два режима:** «проверка с референсом» и «проверка по брифу». Для второго у скилла нет критериев.

### Что исправить

- Реализовать универсальный раннер `npm run qa -- <slug>` (см. дорожную карту): конфигурация проекта в `project.json`, матрица из скилла, JSON-схема результата.
- Оценку делить на **измеряемую программно** (консоль, запросы, overflow, битые изображения, axe, вес) и **экспертную** (композиция, типографика); агент заполняет только вторую, и только после программного отчёта.
- Добавить режим «по брифу» с критериями без референса.

## 4. Качество самих скиллов

| Критерий | Оценка |
|---|---|
| Корректность описания и условий | Хорошая для референса; пробел для брифа |
| Чёткость критериев результата | Средняя: тексты есть, схем нет |
| Полнота инструкций | Высокая, местами избыточная |
| Качество примеров | Низкая: в скиллах нет эталонного прохода с реальными файлами; `generator-knowledge-demo.md` — лучший пример, но он ретроспективный, а «поиск» в нём выполнен вручную (инструмента поиска по базе знаний в репозитории нет) |
| Повторное использование | Хорошая: относительные ссылки на документы |
| Согласованность с DS и между собой | Хорошая по смыслу; плохая по версиям (kit, `overview.md`) |

Размер инструкций: действующие скиллы вместе 15 КБ — приемлемо; проблема в «хвосте» документов, на которые они ссылаются.

## 5. Карта необходимых компетенций и решение «чем закрывать»

Принцип: *скилл* — когда нужна последовательность суждений агента; *инструмент* — когда результат детерминирован; *проверка* — когда можно вынести вердикт машиной; *архитектура* — когда проблема в структуре данных или процесса.

| Компетенция | Чем закрывать | Решение | Приоритет |
|---|---|---|---|
| Анализ требований и план сайта (по брифу) | **Новый скилл** `site-from-brief` | Сценарий уже встречается (house-store), но не описан | P1 |
| Анализ референса | Существующий `site-from-reference` | Улучшить | P1 |
| Информационная архитектура | Часть `site-from-brief` и шаблона `page-blueprint` | Не выделять | — |
| Работа с дизайн-системой и токенами | **Инструмент** (`catalog:search`, `check:tokens`) + архитектура (каталог) | Сначала метаданные, не скилл | P1 |
| Поиск и повторное использование блоков | **Инструмент** + каталог (метаданные в `index.md`) | Не скилл | P1 |
| Композиция страниц, типографика, иерархия | Каталог секций + рубрика в `visual-qa` | Не скилл | P1/P2 |
| Адаптивность | Автопроверка (4 viewport, overflow) | Инструмент | P0 |
| Доступность | **Автопроверка** (axe-core) + пункт чек-листа | Не скилл | P1 |
| Изображения и ресурсы | **Инструмент** (манифест `assets.json`, локализация, оптимизация) + правило в `AGENTS.md` | Не скилл | P0/P1 |
| Производительность, SEO | Автопроверка (вес, `width/height`, `lazy`, meta) | Не скилл | P1 |
| Проверка функциональности интерфейса | Playwright smoke-тесты по контракту `project.json` | Проверка | P1 |
| Визуальная проверка в браузере | Существующий `visual-qa` + раннер | Улучшить | P0 |
| Поиск и исправление ошибок | Цикл внутри `visual-qa` | Не выделять | — |
| Совместимость с платформой (Shop2, legacy) | `adapters/*` + проверка | Отложить: потребности не подтверждены | P2 |
| Сохранение и классификация удачных решений | **Новый скилл** `knowledge-capture` + валидатор | Нужен: главная цель проекта | P1 |
| Анализ прошлых генераций | Часть `knowledge-capture` | Не выделять | P1 |
| Проверка качества знаний | **Инструмент** `kb:validate` + ручное утверждение | Не скилл | P1 |
| Регрессия после изменения DS | **Автопроверка** (диф скриншотов по всем проектам) | Не скилл | P2 |

## 6. Недостающие скиллы

### 6.1 `site-from-brief` — создавать (P1)

1. **Проблема:** сценарий без референса существует (`house-store`), но не определён: нет документов, статусов, критериев качества.
2. **Почему не покрыт:** `site-from-reference` целиком строится вокруг сравнения с референсом.
3. **Вход:** бриф (ниша, аудитория, страницы, функции, тон), ограничения по ресурсам, выбранные записи базы знаний.
4. **Выход:** `brief.md`, `page-blueprint.md`, `token-map.md` со статусами, `project.json`; далее общий путь через сборку и QA.
5. **Интеграция:** общие шаги (карта соответствия, стоп-условия, QA) вынести в общий документ, на который ссылаются оба скилла.
6. **Проверка:** `check:project` + оценка по брифу (соответствие требованиям — экспертная, остальное — программно).
7. **Когда:** сразу после P0, потому что сценарий уже реально используется.

### 6.2 `knowledge-capture` — создавать (P1)

1. **Проблема:** сейчас «извлечь знание» — одна фраза в конце скилла; у знаний нет схемы, поиска, оценки.
2. **Почему не покрыт:** ни один скилл не отвечает за этап после проекта.
3. **Вход:** каталог проекта, `results.json` QA, `token-map.md`, gap-reports, содержимое `custom.scss` (ручные правки — самый ценный сигнал), при наличии git — diff.
4. **Выход:** файлы-кандидаты в `knowledge/inbox/` (не в рабочую базу!), отчёт «что не переносить».
5. **Интеграция:** запускается после приёмки проекта; не меняет DS и скиллы.
6. **Проверка:** схема + дубликаты + правило «два независимых проекта для approved».
7. **Когда:** после схемы знаний и раннера (этапы 3–4 дорожной карты).

### 6.3 Не создавать сейчас

- Отдельные скиллы по типографике, адаптивности, доступности, SEO, производительности, изображениям: детерминированные требования закрываются автопроверками, а суждения — рубрикой внутри `visual-qa`.
- Скилл регрессионного тестирования DS: это CI-задача.
- Скилл совместимости с платформами: нет подтверждённого спроса.
