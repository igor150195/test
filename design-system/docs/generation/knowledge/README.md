# База знаний генератора

Это версионируемый каталог минимальных воспроизводимых решений, а не копия
кода проектов и не новая библиотека компонентов. Он помогает генератору
находить проверенные способы применения существующей дизайн-системы до начала
реализации.

## Структура

```text
knowledge/
├── index.json         # generated by kb:build; machine-readable index
├── registry.yml       # generated by kb:build; do not edit
├── schema/            # JSON Schema for a pattern entry
└── patterns/          # один Markdown-файл на решение с YAML frontmatter
```

Каждый pattern обязан содержать: ID, назначение, категорию, теги, статус,
ссылки на реализацию и пример, токены/компоненты, viewport, результаты
технической и visual QA, ограничения и условия отказа. Поиск начинается с
`registry.yml`, но перед применением необходимо открыть сам pattern и реальные
контракты дизайн-системы: совпадение тега или названия не доказывает
применимость.

`patterns/` — единственный источник истины. `npm run kb:build` детерминированно
пересобирает `registry.yml` и `index.json`; `npm run kb:build -- --check`
проверяет, что производные файлы актуальны.

## Поддерживаемый YAML frontmatter

Парсер намеренно поддерживает только небольшой проверяемый поднабор YAML:

- root scalar keys и inline arrays, например `tags: [hero, responsive]`;
- один уровень вложенного map или списка с двумя пробелами, например
  `requires.tokens` или `evidence.projects`;
- только plain string values и массивы plain string values.

Якоря/алиасы, YAML tags, multiline scalars (`|`/`>`), inline objects,
табуляция, глубокая вложенность и неизвестные типы являются ошибкой с номером
строки. Это не общий YAML-парсер: формат выбран, чтобы не добавлять новую
зависимость и не принимать неоднозначные записи молча.

Обязательный контракт описан в `schema/entry.schema.json`. `requires.tokens`
содержит обязательные токены и проверяется по CSS-контракту. Для hooks с
fallback, которые могут отсутствовать, используйте `requires.optional_tokens`:
их существование намеренно не валидируется. Поле `requires.ds_version` не
поддерживается: у дизайн-системы пока есть только git SHA, а не semver.

## Жизненный цикл

- `candidate` — предложение, извлечённое после проекта и QA. Не является
  разрешением копировать код или расширять API.
- `verified` — есть воспроизводимый пример, зафиксированные проверки и
  ограничения. Всё ещё не является новым публичным API дизайн-системы.
- `approved` — пользователь явно согласовал повторное применение решения.

Повышать `candidate` до `verified` можно только после подтверждённой
технической и визуальной проверки. `approved` требует явного согласования.
Если новое наблюдение показывает ограничение, обновите существующий pattern,
а не создавайте дубликат.

## Работа генератора

1. После анализа референса найти релевантные записи по категории и тегам.
2. Проверить их реальную реализацию, токены, компоненты, viewport и ограничения.
3. Добавить результат проверки в `projects/<slug>/docs/token-map.md`.
4. Использовать только применимый `verified`/`approved` pattern через
   подтверждённые контракты. `candidate` — материал для оценки, не шаблон кода.
5. При отсутствии возможности применить pattern создать `EXTEND` или `BLOCKED`
   по [Design System First](../design-system-first.md), а не локальный обход.
6. После QA извлечь только минимальное повторяемое наблюдение в новый
   `candidate` и связать его с результатами проверки.

## Шаблон pattern

```markdown
---
id: KBP-0000
title: Краткое название
kind: composition
status: candidate
scope: universal
platform: neutral
industry: []
page_types: [home]
tags: [hero, responsive]
requires:
  components: [.ds-button]
  tokens: [--ds-page-gutter]
  optional_tokens: [--focus_ring_color]
variants: []
data_needed: [heading, image]
viewports_checked: [390x844, 1440x900]
evidence:
  implementation: path/to/implementation
  technical_check: path/to/result
  visual_check: path/to/report
  projects: [example]
  limitations: [one project]
review_after: 2027-01-01
supersedes: []
applies_when: [есть изображение]
not_when: [контент без изображения]
---

## Назначение
...

## Ограничения и условия отказа
...
```

## Команды

- `npm run kb:validate` — schema, evidence, tokens, classes, ID и дубликаты.
- `npm run kb:build` — пересобрать производные индексы.
- `npm run kb:build -- --check` — проверить отсутствие ручного расхождения.
- `npm run kb:search -- --status verified --tag hero` — найти не более пяти
  применимых записей. Пустой результат означает продолжить без базы знаний,
  а не читать patterns напрямую или придумывать запись.
