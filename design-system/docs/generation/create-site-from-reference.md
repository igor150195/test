## Требования

1. Сначала изучи актуальный API дизайн-системы и анализируй референс. Не приступай к стилям по одному общему впечатлению.
2. Создай `reference-analysis.md` и `token-map.md` до основной реализации. В анализе зафиксируй зоны header, измеримые параметры hero, статус доказательности каждой секции и mobile-стратегию.
3. Для каждого существенного элемента в `token-map.md` назначь `REUSE`, `COMPOSE`, `EXTEND` или `BLOCKED` по [Design System First](design-system-first.md). Изучи реальные контракты токенов, `.ds-*` компонентов, блоков, иконок и нейтральных миксинов, а не только их имена.
4. Перед картой соответствия найди релевантные записи в [базе знаний](knowledge/README.md), проверь их реализацию, viewport и ограничения; не применяй pattern только по названию. Предпочитай применимые `verified`/`approved` решения.
5. При любом существенном `EXTEND` или `BLOCKED` создай `design-system-gap-report.md` и остановись до реализации затронутых секций, пока пользователь явно не подтвердит расширение или частичный scope. Не заменяй пробел локальными значениями, самодельным компонентом или упрощённой декоративной версией.
6. Только после отсутствия неутверждённых пробелов создай каталог `projects/<slug>`, выполни `npm run project:styles -- init <slug>`, создай `page-blueprint.md` и приступай к реализации. Не перезаписывай существующий `styles/custom.scss`; подключай его скомпилированный CSS после project CSS. Старые общие файлы не меняй ради одного проекта.
7. Воспроизведи порядок секций, пропорции, визуальную иерархию и тип изображений референса в рамках одобренной карты. Не копируй дизайн `home.html` автоматически: это только пример API.
8. Не оставляй placeholder-картинки, фиктивные CTA или lorem-текст в готовом результате без явного обозначения.
9. После реализации обязательно собери проект и, если браузерная среда доступна, открой страницу, сними desktop/mobile screenshots, оцени визуальные расхождения, исправь только несоответствия, покрытые `REUSE`/`COMPOSE`, и пересними. Для navigation, grid или filters проверь также 768 и 1024px. Не указывай путь к PNG, если используемый браузер не умеет сохранить capture.
10. Проведи технические проверки и visual QA по [чек-листу visual QA](visual-qa-checklist.md), включая проверку отсутствия неутверждённых обходов дизайн-системы и порядка подключения custom CSS.
11. Не останавливайся после первой генерации. Выполни хотя бы один полный цикл исправления визуала, пока нет значимых отклонений или пока не станет ясно, что дальнейшее сравнение заблокировано ограничениями входных данных. Сравни итоговый DOM с blueprint и token map, чтобы число карточек, формы, CTA и использованные иконки не расходились с документацией. После подтверждённого QA добавь минимальное предложение в базу знаний со статусом `candidate`.

## Итог

Передай путь к проекту, кратко укажи использованные существующие токены/компоненты, project overrides и причины исключений. Укажи выполненные команды, результаты тестов, пути к скриншотам, score визуального качества и нерешённые проблемы. Никогда не заявляй о проверке, которая фактически не выполнялась.
