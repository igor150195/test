# Changelog генератора сайтов

## 2026-10-20 — программный QA и проверяемая карта Design System First

- Добавлен универсальный `npm run qa -- <slug>` для уже собранного
  `projects/<slug>/dist/`: четыре viewport, first-screen/full-page/segment
  captures, результаты программных проверок в `artifacts/qa/latest/results.json`
  и отдельная пустая до экспертного анализа часть `expert`.
- Добавлена `npm run check:compliance -- <slug>`. Она читает размеченные
  блоки `ds-section` в проектной `token-map.md`, проверяет связи с DS и
  базой знаний, покрытие фактических HTML-секций и pending `EXTEND`/`BLOCKED`.
- Известные token/resource/asset/compliance долги получили причину и даты
  добавления/пересмотра; просроченный долг выводится проверками отдельным
  предупреждением.
- `house-store` получил ретроспективные документы в режиме `brief` по
  фактам кода и QA; `fashion-store` и `test-site` получили только
  подтверждённые записи карты. Pending вкладки `test-site` остаются
  известным нарушением, а не объявлены DS-контрактом.
- QA сохраняет отчёт `technical.a11y` из зафиксированного
  `@axe-core/playwright@4.13.0`, включая непроверенные axe-проверки
  `incomplete`. Его статусы следуют compliance-политике, но пока не меняют
  итоговый технический QA status до отдельного согласования hard-fail.

## 2026-10-19 — contract изолированной поставки проекта

- Добавлены локальные схемы и проверки `project.json`/`assets.json`: проект
  фиксирует Git SHA генератора и дизайн-системы, страницы, владельцев файлов,
  зависимости и статус прав на ресурсы.
- `site:build` создаёт детерминированный `projects/<slug>/dist/`, собирает CSS
  в документированном порядке, копирует SVG-спрайт и заменяет 138 URL-путей
  токенов на относительные. Строгая разметка и отсутствующие локальные ресурсы
  останавливают поставку вместо молчаливой публикации.
- `check:site` проверяет поставку из подкаталога сервера; `check:assets`
  отделяет подтверждённые долги от новых внешних или отсутствующих ресурсов.
- Известный общий URL на отсутствующий `empty_color.svg` и отсутствующий
  `house-store/images/long-line.png` остаются открытыми блокерами: этот этап
  намеренно не меняет ни общий токен, ни проектный CSS.

## 2026-10-19 — стабилизация безопасной генерации и проверок

- `project-styles build` больше не создаёт `styles/custom.scss` неявно и не
  перезаписывает CSS без маркера `/* generated by project-styles */`; пустой
  или comment-only placeholder допускается, а осознанная замена требует
  `--force`.
- Добавлена тестовая защита legacy CSS и сохранения ручного слоя.
- Добавлены `check:docs` (локальные Markdown-ссылки и конфликтующие копии
  инструкций) и `check:tokens` (конфликтные/неопределённые токены и `.ds-*`
  контракты HTML).
- Известные общие дефекты зафиксированы в
  `scripts/known-token-issues.json` как предупреждения до отдельного
  согласованного исправления.
- Удалены устаревший `codex-site-generation-kit/` и пустой
  `design-system/knowledge-base/`; единственными рабочими источниками стали
  `.agents/skills/` и `design-system/docs/generation/`.
- `overview.md` обновлён по фактической структуре, а 13 шагов
  `site-from-reference` получили последовательную нумерацию.

## 2026-10-16 — база знаний и ручной слой проекта

- Добавлена файловая база знаний `generation/knowledge/` с frontmatter,
  статусами `candidate`/`verified`/`approved` и лёгким YAML-индексом.
- `site-from-reference` ищет и проверяет knowledge patterns до реализации, а

- Добавлена проверка сохранности ручного SCSS при повторной инициализации.

## 2026-10-16 — политика Design System First

Для новых сайтов генератор больше не имеет права компенсировать пробелы
дизайн-системы локальными токенами, самодельными компонентами, произвольными
визуальными значениями или упрощёнными заменами референса.

- Добавлен единый документ [Design System First](design-system-first.md) с
  четырьмя обязательными статусами: `REUSE`, `COMPOSE`, `EXTEND`, `BLOCKED`.
- `site-from-reference` создаёт карту статусов до проектного кода и останавливает
  генерацию при неутверждённом `EXTEND`/`BLOCKED`, требуя gap report.
- `visual-qa` и его чек-лист теперь проверяют соответствие итогового кода карте,
  а не только рендер и техническое состояние.
- `AGENTS.md`, generator guide, prompt и template анализа ссылаются на единый
  источник правил вместо дублирования длинной политики.

Это изменение не затрагивает токены, компоненты, блоки, SCSS API или проекты.

## 2026-10-15 — выводы из диагностики первого проекта

Источник фактов: [generator-review.md](../../../projects/fashion-store/docs/generator-review.md).
Изменения ниже намеренно не меняют CSS API, токены, компоненты и блоки: один
проект не даёт достаточного основания расширять общую дизайн-систему.

## Классификация найденных проблем

### 1. Исправления только для `fashion-store`

| Проблема | Почему это не системная доработка | Следующее действие |
|---|---|---|
| Категории стоят под hero, хотя в доступном desktop-референсе они находятся в utility-навигации. | Это подтверждённое расхождение одной конкретной страницы; существующие HTML-ссылки и блок Header уже позволяют разместить их локально. | Изменять только проект после отдельного согласования. |
| Текст hero расположен приблизительно по центру и не повторяет измеренную вертикальную опору референса. | Позиция зависит от конкретного изображения, crop и текста. | Настроить локальный hero по измерениям. |
| Бренды на 390px обрезаются, а поиск ведёт к скрытому полю. | Это результат конкретных media rules и локальной разметки. | Определить локальное поведение ленты и поиска. |
| Резкая смена палитры в editorial-секции. | Нужна оценка именно выбранного изображения и роли этой секции. | Скорректировать local art direction только при доступном референсе/брифе. |

### 2. Улучшения дизайн-системы, полезные для нескольких проектов

| Предложение | Повторится на других сайтах? | Системная причина подтверждена? | Решается текущими токенами/компонентами? | Как проверить пользу |
|---|---|---|---|---|
| Документировать единый проектный contract для ширины контейнера, legacy `--site_width` и `--ds-container-max`. | Вероятно, пока проекты используют Header/Footer и Product Card вместе. | Да: Header/Footer читают `--site_width`, Product Card читает `--ds-container-max`, а `spacing.css` делает второй alias первого. | Да, без нового токена: для общей ширины достаточно `--site_width`. | Создать второй проект с Header, Footer и Product Card; изменить только `--site_width` и проверить одинаковые границы контейнеров. |
| Документировать поддерживаемые точки тематизации Product Card до расширения API. | Возможно, но один пример не доказывает потребность в новом API. | Частично: локальный CSS переопределял плотность карточки, но это один проект. | Частично: существующие классы и project-local CSS позволяют это сделать. | Собрать минимум два независимых проекта; расширять component API только если им нужен один и тот же override. |

В этой итерации реализован только первый пункт как уточнение
`generator-guide.md` и `site-from-reference`: общая ширина задаётся через
`--site_width`, а `--ds-container-max` не дублируется без намерения разделить
контейнеры. Второй пункт остаётся наблюдением, а не поводом создавать токен или
вариант компонента.

### 3. Недостающие правила `site-from-reference`

| Правило | Повторится на других сайтах? | Системная причина подтверждена? | Нужны ли новые токены/компоненты? | Как проверить пользу |
|---|---|---|---|---|
| Карта зон Header до реализации: utility, primary/context nav, logo, search, actions. | Да: все сайты с многослойной шапкой рискуют потерять иерархию. | Да: первый проект переместил подтверждённые категории в другую зону. | Нет. | Сравнить карту с итоговым DOM и с одинаковым screenshot reference. |
| Маркировать каждую секцию как наблюдаемую, выведенную или project-specific. | Да при частичном URL/screenshot. | Да: нижняя часть референса была недоступна, а локальный blueprint описал неподтверждённую композицию как план. | Нет. | Проследить, что все непроверяемые секции отчёта явно помечены и не выдаются за совпадение. |
| Фиксировать hero: anchor текста, crop/focal point, число строк и видимые controls. | Да: hero определяет восприятие первого экрана. | Да: позиция первого hero была определена приближённым `50%`, а controls референса не попали в реализацию. | Нет. | Сравнить измеренные границы hero в reference/local на одном viewport. |
| Вести asset inventory: источник, ratio, crop/focal point, роль, палитра, fallback. | Да для image-led сайтов. | Да: изображения первого проекта внешние и не имеют manifest/fallback. | Нет. | Проверить 0 broken resources, описанные crop и согласованность full-page palette. |
| Перед передачей сверять blueprint/token map с конечным DOM. | Да. | Да: в docs были заявлены 6 карточек/форма и icon token, которых нет в HTML. | Нет. | Автоматический или ручной чек-лист не находит расхождений в числе элементов, CTA, классах и icon tokens. |
| Задокументировать responsive policy на 390/768/1024/1440. | Да для navigation, grids и filters. | Да: проверенный mobile показал клиппинг брендов и скрытую цель поиска. | Нет. | На каждом viewport отмечены visibility/order/scroll/action; ссылки не указывают на скрытые цели. |

## Остающиеся проблемы

1. Браузерный интерфейс этой среды всё ещё не экспортирует PNG в репозиторий. Инструкция фиксирует ограничение, но не заменяет инструмент экспорта.
2. Нет второго независимого сайта, чтобы подтвердить необходимость нового API тематизации Product Card. Новые component tokens или variants не добавлены намеренно.
3. Не реализована автоматическая DOM/document consistency проверка; пока она описана как обязательный ручной шаг.
4. Нет механизма overlay/diff reference-local. Skill требует измерений и одинаковых регионов, но не обещает недоступный инструмент.
