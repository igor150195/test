# Design System First

## Назначение

Генератор сайта сначала доказывает, что референс можно воспроизвести средствами существующей дизайн-системы, и только затем начинает реализацию. Он не компенсирует пробелы самодельными токенами, компонентами, локальными визуальными API или упрощёнными заменами.

Это правило не запрещает разметку проекта и layout-композиции. Они допустимы, когда используют подтверждённые публичные токены, компоненты, блоки и их документированные контракты. Проектный CSS не должен становиться параллельной дизайн-системой.

## Обязательная карта соответствия

До HTML, CSS, SCSS или JavaScript изучить референс, документацию, реализацию и варианты существующих токенов, компонентов, блоков, миксинов и иконок. Для каждого существенного элемента зафиксировать в `projects/<slug>/docs/token-map.md` один статус:

| Статус | Значение |
|---|---|
| `REUSE` | Существует подходящий публичный ресурс; применяется по его контракту. |
| `COMPOSE` | Композиция собирается из существующих ресурсов без новых визуальных значений и API. |
| `EXTEND` | Необходим повторно применимый ресурс дизайн-системы: токен, вариант, компонент, паттерн или адаптивный контракт. |
| `BLOCKED` | Качественная реализация требует отсутствующего системного ресурса либо недоступных исходных данных. |

`REUSE` и `COMPOSE` нельзя присваивать решению, основанному на произвольных цветах, размерах, радиусах, тенях, типографике, самодельном компоненте или упрощённой замене значимого элемента референса.

## Стоп-условие

Если в карте есть существенный `EXTEND` или `BLOCKED`, не реализовывать затронутые секции и не заменять их временным CSS. Создать `projects/<slug>/docs/design-system-gap-report.md`, описать все пробелы до реализации и дождаться явного подтверждения пользователя. Частичная реализация возможна только при явно данном разрешении и должна ограничиваться элементами `REUSE`/`COMPOSE`.

## Формат gap report

Для каждого пробела указать:

1. секцию и элемент референса;
2. нужный визуальный, интерактивный или адаптивный контракт;
3. проверенные существующие файлы и API;
4. почему они не подходят;
5. отсутствующий системный ресурс;
6. предлагаемое изменение дизайн-системы, его повторную применимость и визуальный компромисс без него;
7. затрагиваемые файлы, публичные контракты, проекты и необходимые проверки.

После одобрения расширение сначала реализуется, документируется и проверяется в самой дизайн-системе. Только затем его разрешено применять в проекте.

## Проверка соблюдения

Visual QA дополнительно проверяет: необъявленные/неподтверждённые токены, произвольные visual values вместо системного контракта, дублирование компонентов, несанкционированные глобальные переменные, разрастание локальных override и упрощённые замены элементов референса. Успешная сборка не делает такие нарушения допустимыми.
