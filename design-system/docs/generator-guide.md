# Руководство для генератора сайтов

## Старт нового сайта

Соберите дизайн-систему из корня репозитория (`npm run build`) и подключите
готовые файлы в указанном порядке:

```html
<link rel="stylesheet" href="/dist/css/tokens.css">
<link rel="stylesheet" href="/dist/css/core.css">
<link rel="stylesheet" href="/dist/css/components.css">
<link rel="stylesheet" href="/dist/css/blocks.css">
```

`tokens.css` содержит CSS-переменные, `core.css` — reset, доступность и
базовую типографику, `components.css` — независимые компоненты, а `blocks.css`
— составные блоки. Не подключайте `legacy-platform.css`, если проект не
использует подтверждённую интеграцию с Shop2, Remodal или legacy `gr-*`.

Для запуска шаблона используйте [home.html](../templates/home.html) как
структурный ориентир. При локальном просмотре сервер должен раздавать корень
репозитория: URL иконок в `icons.css` начинаются с `/design-system/sets/`.

## HTML-контракты

Используйте только публичные классы и вложенность из документации компонента
или блока. Основные контракты находятся рядом с исходниками:

- `design-system/components/*/index.md` — Button, Icon, Icon Button, Form,
  Rating, Price, Counter и Badge;
- `design-system/blocks/*/index.md` — Header, Product Card и Footer.

Например, кнопка получает `.ds-button` и один вариант
`.ds-button--primary|secondary|ghost|accent|white`; иконка передаёт реальный
токен реестра через `style="--ds-icon: var(--icon_...)"`; карточка товара
собирается из `.ds-product-card` и её документированных `__`-элементов.

Не переносите в новый проект разметку Shop2, Remodal, `gr-*` или legacy
миксины как часть нейтрального API. Для интерактивных элементов используйте
нативные `button`, `input`, `label` и доступные имена (`aria-label` для кнопки
только с иконкой). Не вкладывайте кнопки в ссылки.

## Настройка внешнего вида

Сначала используйте текущие токены из `design-system/tokens/new_colors.css`,
`new_sizes.css`, `fonts.css` и `icons.css`. Не добавляйте в проектную тему
произвольные цвета, размеры, отступы, радиусы, тени или типографику как
замену отсутствующему API. Перед реализацией сайта по референсу обязательна
[карта соответствия Design System First](generation/design-system-first.md).
Если ей требуется `EXTEND` или `BLOCKED`, подготовьте gap report и дождитесь
подтверждения; не маскируйте проблему локальным CSS.

Тематическое переопределение существующего публичного контракта на селекторе
проекта допустимо только после того, как карта доказала его применимость и
проект не создаёт новый визуальный API. Не создавайте произвольные иконки или
ID: используйте только переменные из `icons.css`. О доступных токенах и
известных ограничениях читайте в [tokens.md](tokens.md) и [icons.md](icons.md).

Сейчас `--ds-container-max` является alias для `--site_width`. Header и Footer
напрямую используют `--site_width`, а product-card grid — `--ds-container-max`.
Для единой ширины страницы переопределяйте только `--site_width`: alias
подхватит значение. Одновременно задавать оба токена следует лишь при
осознанном разделении ширины контейнеров; это не требуется по умолчанию.

## Проверяемая генерация по референсу

Перед вёрсткой используйте [шаблон анализа](generation/reference-analysis-template.md):
зафиксируйте зоны шапки, измеримые параметры hero, статус доказательности
каждой секции, responsive-поведение и манифест изображений. В `token-map.md`
назначьте каждому существенному элементу `REUSE`, `COMPOSE`, `EXTEND` или
`BLOCKED`. Недоступная часть референса — это проектное допущение, а не
подтверждённая реплика.

Перед картой соответствия ищите аналогичные решения в
[базе знаний генератора](generation/knowledge/README.md). Открывайте найденный
pattern и его реальную реализацию: теги не заменяют проверку контрактов,
viewport и ограничений. Применимыми по умолчанию считаются только `verified`
и `approved`; `candidate` — предложение для исследования. После QA извлекайте
из проекта минимальное повторяемое наблюдение как новый `candidate`, не копию
всего project CSS.

## Ручной слой проекта

Новый проект разделяет сгенерированные и ручные стили:

```text
styles/project.scss  → css/project.css
styles/custom.scss   → css/custom.css
```

`styles/custom.scss` создаётся командой `npm run project:styles -- init <slug>`
только при отсутствии и подключается после всех общих и проектных CSS. Он
предназначен для владельца сайта, поэтому повторная генерация не может его
перезаписывать, очищать, переносить или включать в дизайн-систему. Скомпилируйте
его командой `npm run project:styles -- build <slug>`; для существующего
проекта с занятым `css/custom.css` укажите отдельный выходной путь, например
`npm run project:styles -- build <slug> css/custom-overrides.css`, и подключите
его последним. Полный шаблон: [templates/project](../templates/project/README.md).

После реализации сверяйте `page-blueprint.md` и `token-map.md` с финальным
HTML: порядок секций, число карточек, формы, CTA, публичные классы и icon-токены
должны совпадать. Для visual QA используйте
[чек-лист](generation/visual-qa-checklist.md); если браузер не может сохранить
скриншоты в проект, укажите это явно вместо фиктивных путей к файлам.

После изменений запускайте `npm run build` и `npm run check:sass`. Шаблон и
витрина — статические примеры: маршруты, данные товаров и обработчики действий
должен предоставить конкретный проект.
