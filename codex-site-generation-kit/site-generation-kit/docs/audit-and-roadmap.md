# Аудит готовности дизайн-системы к генерации сайтов

## Резюме

Система уже пригодна как техническая база для сборки новых сайтов, но ещё не является воспроизводимым конвейером создания качественного дизайна по референсу. Основной пробел — не нехватка CSS, а отсутствие управляемого цикла: **понять референс → сопоставить его с существующими токенами → спроектировать структуру → реализовать → отрендерить → сравнить → исправить → проверить повторно**.

Оценка архитектурной готовности — около **55%**. Это экспертная оценка состава репозитория, а не формальный тест дизайна. Без браузерного рендера нельзя достоверно оценить фактическое визуальное качество шаблонов.

## 1. Что уже хорошо

- Исходники разделены на токены, core, компоненты, блоки, адаптеры, шаблоны и документацию.
- Есть большой существующий словарь CSS custom properties и SVG-спрайт с реестром иконок.
- Есть независимый API-кандидат `.ds-*` для кнопок, иконок, полей, чекбоксов/радиокнопок, рейтинга, цены, счётчика и бейджей.
- Есть универсальные блоки Header, Product Card и Footer с HTML-контрактами.
- Есть `home.html`, `shop.html` и showcase; это хорошая основа для фикстур и каталога примеров.
- В `AGENTS.md` правильно задан приоритет переиспользования существующих переменных и запрет на бесконтрольное изменение legacy API.
- Разделение нейтрального API и платформенно-зависимых Shop2/Remodal/legacy-миксинов — правильное архитектурное направление.

## 2. Что сейчас мешает качественной генерации

### P0 — исправить до активного использования генератора

#### 2.1. Устаревшая документация

`design-system/docs/overview.md` утверждает, что сборки, демонстрационного проекта, компонентов и блоков нет. В текущем архиве они уже присутствуют: есть `package.json`, SCSS entrypoints, `templates/home.html`, `templates/shop.html`, showcase, `.ds-*` компоненты и блоки. Поэтому агент, который честно читает документацию, получает неверную карту проекта.

**Действие:** обновить overview по фактической структуре. У каждой документации должны быть метаданные `status`, `last_verified` или эквивалентная отметка версии/даты, а также ссылка на соответствующий исходный файл.

#### 2.2. Цветовые переопределения частично ломают тему

В `new_colors.css` базовые `--primary` и `--accent` заданы отдельно от заранее рассчитанных оттенков `--primary_1…9`, `--accent_1…9` и некоторых surface-значений. Если проект переопределит только `--primary`, оттенки и hover/active-состояния могут остаться в исходной фиолетовой палитре.

**Действие:** определить официальный способ тематизации. Предпочтительно иметь проектный `theme.css`, где тема согласованно задаёт семантические цвета и их производные, либо перевести производные значения на поддерживаемый и проверенный способ вычисления. Не просить генератор менять только `--primary` и считать палитру готовой.

#### 2.3. Есть известные дефекты токенов и ресурсов

В `tokens.md` уже отмечены:

- отсутствующие `--icon_rating_star_lg`, `--icon_site_checkbox` и `--icon_site_checkbox_small`;
- ссылка на отсутствующий `empty_color.svg`;
- конфликт двух объявлений `--toggle_title_icon_h` (высота, затем URL-переменная);
- точные дубли некоторых gap-переменных;
- ошибки/неоднозначности имён;
- неудовлетворительный контраст некоторых существующих пар `--on_success` / `--success`, `--on_sale` / `--sale`, `--on_error` / `--error` согласно текущему аудиту токенов.

**Действие:** завести список дефектов токенов с владельцем, статусом, областью влияния и решением по обратной совместимости. Исправлять сначала ресурсы, реально нужные нейтральным `.ds-*` компонентам и шаблонам, не переименовывая массово legacy API.

#### 2.4. Проверка сборки не равна проверке сайта

`check.scss` проверяет компиляцию существующих mixins. Sass-компилятор не проверяет наличие всех runtime CSS-переменных, корректность URL-иконок, переносы текста, переполнение контейнеров, качество изображений или сходство со скриншотом.

Во время аудита `npm run build` в распакованном архиве завершился на `sass: Permission denied` — файл `node_modules/.bin/sass` не имел executable-бита в архиве. Прямой запуск `node node_modules/sass/sass.js …` прошёл и компилировал SCSS, но выдавал предупреждения о deprecated `@import` и делении через `/` в Sass. Следует перепроверить `npm ci` в обычной рабочей среде, прежде чем считать сам build script неисправным.

**Действие:** оставить Sass smoke-check и добавить проверки runtime-токенов, иконок, HTML и визуальных скриншотов. Сначала не нужно мигрировать весь SCSS на `@use`: это отдельная техническая задача после создания стабильного конвейера.

### P1 — сделать дизайн предсказуемым

#### 2.5. Нет полноценной шкалы отступов и layout-токенов

Есть `--section_pd_desktop/laptop/tablet/mobile`, а компонентные семейства содержат собственные gap/padding. Но нет единой общеупотребимой шкалы для внутреннего ритма и нет достаточного различия между:

- расстоянием между текстом и кнопкой;
- расстоянием между карточками;
- вертикальным отступом секции;
- внешним полем страницы;
- шириной контейнера.

В текущих универсальных блоках некоторые существующие переменные используются не по смыслу, например `--small_radius` выступает в роли gap, а `--sm_btn_gap` используется как общий layout-отступ. Это формально работает, но делает токены неочевидными и мешает настройке отдельного сайта.

**Действие:** добавить узкий слой foundation-токенов отступов и сетки. Старые переменные оставить совместимыми, а компоненты мигрировать постепенно. Подробная схема — в `spacing-scale-proposal.md`.

#### 2.6. Слишком мало готовых секций для разных типов сайтов

Header, карточка товара и Footer не покрывают полноценную композицию страницы. Для качественной генерации нужны документированные секции и сценарии компоновки: hero, текст+изображение, список преимуществ, категории, баннер, логотипы/социальное доказательство, отзывы, FAQ, CTA, подписка, статьи, услуги/кейсы и пустые состояния.

**Действие:** не добавлять бесконечный набор компонентов сразу. Начать с секций, которые повторяются в эталонных типах сайтов, и обеспечить каждой секции 2–3 варианта композиции, responsive-правила и HTML-пример. Делать секции композиционными блоками, а не огромными универсальными компонентами с десятками булевых флагов.

#### 2.7. Не определён контракт тематизации нового проекта

Генератору нужно чётко знать, какие изменения разрешены на уровне проекта, а какие затрагивают общую систему.

**Действие:** в каждом проекте создать `theme.css` или `theme.scss`, где хранятся только осознанные переопределения публичных токенов. Не править общие исходники ради одного сайта. Если токена не хватает, записывать gap в `docs/token-map.md` и выбирать один из вариантов: существующий ближайший токен, локальная компонентная переменная, новый общий токен после обоснования.

### P2 — качество визуального результата

#### 2.8. Нет обязательного этапа браузерного рендера и визуальной итерации

Это главный риск. Агент может написать валидный HTML/CSS, который выглядит посредственно: изображение не того масштаба, непохожая сетка, недостаточная иерархия, неровные расстояния или неудачный мобильный перенос.

**Действие:** установить доступный инструмент браузерной автоматизации (предпочтительно Playwright с Chromium или эквивалент, доступный Codex). На каждый проект делать скриншоты минимум desktop + mobile; при наличии референса — сопоставлять соответствующие области side-by-side. Затем исправлять самые заметные отличия и повторять снимки.

#### 2.9. Шаблоны не должны диктовать дизайн референса

`home.html` и `shop.html` полезны как структурные примеры, но не как визуальный шаблон для любого сайта. В них есть демонстрационная фиолетово-зелёная палитра, стилизованные SVG-заглушки изображений и встроенные page styles. Они показывают использование `.ds-*`, но не подходят в качестве универсальной арт-дирекции.

**Действие:** прямо указать генератору, что шаблон является стартовой структурой/API-примером. Для реального проекта выбирать композицию, палитру, типографику и изображения по референсу. Если сайт продаёт товары/услуги, не оставлять геометрические заглушки там, где нужны реальные изображения.

## 3. Рекомендуемая архитектура конвейера

```text
URL / screenshot / набор скриншотов
        ↓
01. Reference analysis
    структура, размеры, секции, типографика, палитра, изображения, состояния
        ↓
02. Token mapping
    сопоставление с текущими токенами; фиксированный список исключений
        ↓
03. Page blueprint
    карта страниц и секций, приоритеты, повторное использование блоков
        ↓
04. Project scaffold
    проект из шаблона, локальная тема, страницы, assets, маршруты/данные
        ↓
05. First implementation
    сначала крупная композиция, потом детали
        ↓
06. Browser render
    сборка, desktop/mobile screenshots, ошибки консоли и ресурсов
        ↓
07. Visual QA + iteration
    исправить 3–5 самых заметных несовпадений, повторить рендер
        ↓
08. Acceptance gate
    визуальный балл + технические проверки + итоговый отчёт
```

Ни один шаг не должен пропускаться только потому, что код компилируется.

## 4. Пошаговый план внедрения

### Шаг 1. Зафиксировать фактическое состояние системы

- Исправить `docs/overview.md`.
- Обновить README/guide с правильными командами запуска и актуальными файлами.
- Отметить, что `home.html`/`shop.html` — примеры, а не обязательный визуальный стиль.
- Удалить из релизных архивов `node_modules/` и генерируемый `dist/`, если они не нужны как артефакты; сохранять `package-lock.json`.

**Готово, когда:** карта проекта больше не противоречит репозиторию, новый агент понимает, где source, где output, какие API нейтральные, какие legacy.

### Шаг 2. Закрыть технические дефекты токенов

- Исправить/заменить отсутствующие иконки и `empty_color.svg` либо явно объявить соответствующие legacy-варианты неподдерживаемыми.
- Разрешить конфликт `--toggle_title_icon_h` и дубли.
- Исправить тематизацию производных цветов.
- Повторно проверить контраст; контрастные пары должны проходить выбранные требования доступности.
- Создать валидатор переменных и URL-иконок как отдельную проверку.

**Готово, когда:** нет необъяснённых runtime-переменных и сломанных ресурсов в публичном нейтральном API, а theme overrides не оставляют смесь старой и новой палитры.

### Шаг 3. Ввести foundation-spacing/layout слой

- Добавить шкалу отступов (предлагается 4px base scale).
- Добавить отдельные page gutter, ширину контейнера, межколоночный gap и вертикальный шаг секций.
- Использовать новые токены в универсальных блоках и примерах.
- Не переписывать весь legacy `new_sizes.css`; вести совместимую миграцию.

**Готово, когда:** новый проект можно оформить без заимствования случайного `--sm_btn_gap` или `--small_radius` для layout.

### Шаг 4. Создать каталог эталонных секций

Минимальный первый набор:

1. Header и Footer (уже есть; улучшить варианты и проверить responsive).
2. Hero: текст слева/справа, overlay/image-led, компактный hero.
3. Сетка карточек: товары, услуги, статьи.
4. Категории/каталог.
5. Преимущества/иконки.
6. Текст + изображение.
7. Социальное доказательство/отзывы.
8. FAQ.
9. CTA/баннер.
10. Формы контакта/подписки.

У каждого блока: назначение, HTML API, ограничения, responsive-контракт, пример, состояние без изображения/без данных.

### Шаг 5. Создать два skills и держать их узкими

- `site-from-reference`: только поток создания проекта из URL/скриншота, включая token map и обязательный браузерный рендер.
- `visual-qa`: только рендер, аудит визуальных/технических дефектов и итерации исправления.
- Позже при реальной потребности добавить `design-system-maintenance` для изменений общей системы. Не стоит сразу создавать много маленьких скиллов без проверенного рабочего процесса.

Основные правила проекта оставлять в `AGENTS.md`, подробные процессы и шаблоны — внутри skills и docs. Это упрощает поддержку и не перегружает каждую задачу лишним контекстом.

### Шаг 6. Сделать локальный browser loop воспроизводимым

- Установить Playwright/Chromium или подтвердить доступный Codex browser tool.
- Команда должна запускать сайт локально и снимать скриншоты desktop и mobile.
- Добавить проверки HTTP-ресурсов/битых изображений, ошибок консоли и горизонтального overflow.
- Сохранять screenshot-артефакты в каталоге проекта, например `artifacts/qa/`.
- Если доступен скриншот референса, хранить исходник в `reference/` и сопоставлять с тем же viewport.

**Готово, когда:** генерация завершается не только файлами, но и доказательством работающего рендера.

### Шаг 7. Провести eval-прогоны

Подготовить 10–20 разнообразных заданий:

- URL главной страницы интернет-магазина;
- скриншот корпоративного сайта;
- mobile-only скриншот;
- референс без доступных изображений;
- сайт с двумя-тремя типами страниц;
- референс, в котором часть элементов не помещается в текущую библиотеку компонентов.

Для каждого задания проверять: выбран ли подходящий skill, создана ли карта референса, использованы ли имеющиеся токены, выполнена ли сборка, сняты ли скриншоты, исправлены ли топовые визуальные отклонения и честно ли описаны ограничения.

### Шаг 8. Только после этого повышать автономность

Не требовать от агента согласования каждого локального токена внутри нового проекта. Требовать фиксации и ревью тех решений, которые меняют глобальный API дизайн-системы. Иначе процесс будет либо слишком медленным, либо будет соблазнять агента обходить ограничения inline-стилями.

## 5. Что должно лежать в каждом новом проекте

```text
projects/<project-slug>/
├── README.md
├── index.html (или entrypoint выбранного стека)
├── pages/
├── assets/
├── styles/
│   ├── theme.css       # только осознанные project-level overrides
│   ├── layout.css      # только layout конкретного сайта
│   └── project.css
├── scripts/            # только когда нужна функциональность
├── reference/
│   ├── source.md       # URL, дата и размеры исходных скриншотов
│   └── screenshots/
├── docs/
│   ├── reference-analysis.md
│   ├── token-map.md
│   ├── page-blueprint.md
│   └── qa-report.md
└── artifacts/qa/        # screenshots и результаты проверок; при необходимости добавить в .gitignore
```

Файлы `pages/`, `styles/` и `scripts/` можно адаптировать к выбранному фреймворку. Главное — не смешивать общие токены и блоки дизайн-системы с одноразовыми решениями отдельного сайта.

## 6. Как измерять качество результата

Визуальный score помогает направлять итерации, но не заменяет технические тесты. Рекомендуемые веса в `visual-qa-checklist.md`:

- 25% — структура, порядок и пропорции секций;
- 20% — изображения, кадрирование и визуальное направление;
- 15% — типографическая иерархия и переносы;
- 15% — отступы, сетка и выравнивание;
- 10% — палитра и контраст;
- 5% — компоненты, границы, тени и состояния;
- 10% — адаптивность.

Ориентир при приёмке — 85/100 или выше, при этом критические ошибки не допускаются независимо от суммы. Если референс неполный или URL недоступен, балл нужно пометить как provisional, а не выдавать за точное сравнение.

### Критические блокеры

- страница не запускается или есть ошибка сборки;
- отсутствует значимая часть первого экрана;
- есть заметный horizontal overflow на целевом мобильном viewport;
- сломаны крупные изображения/иконки;
- текст или интерактивные элементы накладываются друг на друга;
- ключевой CTA/навигация не читаются или не работают;
- генератор заявил о визуальной проверке, но фактически не снимал/не открывал рендер.

## 7. Чего не делать

- Не заменять анализ референса одним общим промптом «сделай красиво».
- Не переопределять один `--primary`, не проверив зависимые цвета.
- Не вводить много новых переменных для каждого элемента сайта; сначала искать существующий токен и его семантику.
- Не заставлять все проекты выглядеть одинаково только потому, что есть `home.html`.
- Не считать компиляцию CSS доказательством визуального качества.
- Не оставлять после первого прохода placeholder-изображения, случайные lorem-тексты, нерабочие ссылки и фиктивные кнопки без явного обозначения.
- Не менять публичные legacy tokens/mixins ради одного нового сайта без оценки обратной совместимости.

## 8. Документация Codex и skills

В текущем архиве `/.agents/skills/` не содержит готовых skills. Рекомендуемая точка старта — два узких процесса в этом пакете. На практике skills следует делать короткими по назначению и переносить подробные шаблоны/чек-листы в supporting docs; для поддержки качества понадобятся небольшие eval-наборы и воспроизводимые проверки.
